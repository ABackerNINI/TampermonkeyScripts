# 分批评审 (Code Review)

设计主轴是**判断与机械分离**: 批次判定、相关性裁决、severity 定级是 agent 的判断; 引文校验、规模分档、锚点推进是脚本的机械。机械面在 `.commands/review/`: `commands run review.pack`(评审包生成)与 `commands run review.check`(引文校验); task id 保留, 包体精简由后续会话负责。

## 铁律

> **一批一评, blocker 清零再进下一批; 收口只补接缝终审。**

评审单元是**批**, 不是任务。任务可以有很多批; 批次边界由"上一次评审过的提交"机械决定, 不由 agent 感觉决定。评审固定发生在该批**提交之前**; 已提交的提交不回头重评。

## ① 触发与豁免

| 触发 (必须评审) | 不触发 (跳过) |
|---|---|
| 可评内容(代码 + 事实性文档)**>0 行** —— 每笔可评提交必评, 不论行数 | 仅**生成物**与**记账类**文件(任务档案/会话切片/基线切片)改动, 机械排除不计行 |
| 触碰**安全敏感面/红线**(不论行数) | |
| 任务**收口**: 另加一次接缝终审 | |

- **取消按任务类型/立档阈值的豁免**: 有没有档案、是不是"小修", 都不再决定要不要评。判据只看**改动面与可评行数**。
- **取消"中途提交不触发"**: 中途提交正是批次边界 —— 每批收尾都要评, 不是留到收口一次评。
- **纯文档任务也要评**(文档错误会直接误导后续会话), 但只评**事实性文档**(计划/报告/约定/坑档/README/AGENTS.md); 档案与切片是记账。
- **收口判定**仍由 agent 判("本次收尾是否该任务最后一次"), 拿不准就问用户一句。收口那次**不重评代码**, 只做 ② 的接缝终审。
- 安全敏感面含 `resources-do-not-track/` 红线(私有整页与凭据)、凭据、网络与 state 写入; 命中即必评, 不因行数少而免。

## ② 批次与容量

- **批次范围** = 上一条已评审的提交 → 当前工作树(含未提交改动)。锚点由 `review.pack` 从 git 历史现算, agent 不用填 hash; 冷启动(历史里一条都没有)时起点退化为 HEAD, 只算工作树 —— 此后漏评的提交一律滚进下一批。
- **建议上限 400 行/批**。依据不是"agent 读不动", 而是**产出密度**: 切得细发现得多, 但每次派发有成本, 且切到低于"一个自包含变更"会切断跨块问题。
- **超 400 行 → 拆批**(按可独立验证的文件组; 拆完仍按两档走), 不是分面; 确实不可拆的残余批 → 派发 ≥2 个子代理。
- **收口接缝终审 ≤200 行**: 只看跨批接缝 —— 接口/数据结构在批与批之间漂移、同一机制被两批各造一套、测试面遗漏、偏离计划; **不重评已评过的代码**。子代理无记忆, 没有任何一批的评审者能看见全局, 这是终审唯一不可替代的职责。相关的 blocker/major/minor 修完才可收尾, 计划外入池; 接缝修复引出的新改动照 ⑤ 的扳机走复评循环。

## ③ 评审包

`commands run review.pack --base <上一条已评审提交>` 生成机械五件: 基线 hash / **评审规模与 400 行分档提示**(行数由脚本实算, 记账类/生成物/二进制不计行)/ 改动文件清单(可评面; 排除面另列, 不入清单)/ 红线命中预警 / **基哈希**(整批过滤 diff 哈希)。`--base` 与脚本锚点不一致时打可见警告, 改用锚点重跑。

- **指路四件**(主 agent 随评审包给出): 档案/计划路径(验收标准 = 档案「原始请求」)、涉及模块清单、安全敏感面(凭据/网络/state 写入/`resources-do-not-track/` 红线)、批次 base hash。
- **禁整库扫描**; reviewer 可读周边代码判调用面, 但发现只收评审包范围内的改动。
- 留痕要用到的日期与取时一律走 `commands run kb.time`, 禁用模型上下文里的日期与手工推算(见 ⑦)。

## ④ 派遣协议

| 档 | 条件 | 拓扑 |
|---|---|---|
| 全能 | 批 ≤400 行且未触安全敏感面 | 1 个子代理全量评审 |
| 分面 | 批 ≤400 行但触安全敏感面 | 2–3 个子代理按面拆(正确性 / 安全 / 测试缺口), 主 agent 合并去重 |
| 拆批 | 批 >400 行 | 先拆批, 拆完按上面两档走 |

> 分面代理**逐个串行派遣**: 宿主并发上限会拒收并发派遣, 逐个重派即恢复。

**reviewer 只读** —— 修复一律主 agent 执行。派遣提示**照抄三件套**, 不临场发挥:

> 1. **只读契约**: 禁止**一切写操作** —— git 状态变更(sync/rebase/merge/stash/checkout/commit/push)、写任何文件、跑写类 task 一律禁止; 只允许读命令(`git rev-parse` / `git diff` / `git show` 属读命令)。
> 2. **范围钉死**: diff 范围 = 评审包基线 `<base>`; 自检锚 = 派遣时 HEAD `<head>`(`git rev-parse HEAD` 现取); 只读快照由 `review.pack` 统一提供, agent 不另建评审副本。
> 3. **开工自检**: `git rev-parse HEAD` ≠ 自检锚 `<head>` → **停手报告, 不评审**; 工作树出现评审包未声明的改动同样停手。

评审交回后主会话**收尾复核**: `git rev-parse HEAD` 仍 == 自检锚, 否则评审期间树被动过 —— 发现作废, 重新锚定后重评。修复增量触发复评时, 以最新一轮 `review.pack` 的上下文评。

## ⑤ 产出与裁决

**产出 schema**(reviewer 输出 JSON 数组, 逐条七字段):

```json
{"file": "相对路径", "line": 42, "quote": "单行内连续引文", "severity": "blocker|major|minor|nit", "claim": "问题一句话", "relevance": "相关|不相关", "fix": "修法一句话"}
```

- `quote` 必须是**单行内连续片段**; `commands run review.check --findings <json>` 逐条校验: 引文与源码逐字比对(行号允许 ±3 邻近)、字段齐、severity/relevance 枚举合法。**refute 的条目直接弃, 不复核** —— 幻觉引文是 LLM 评审的头号失效模式。
- reviewer 指令里显式写"**不报清单**": 理论风险(说不出具体失败场景)/ 未改动代码 / 风格偏好 / 库推荐, 一律不报。
- **相关性裁决**(主 agent, reviewer 初判仅参考): 相关 = 属于本批计划目标之内, **或**由本批改动直接引入/直接暴露; 其余一律按 create-issue skill 入池。拿不准 → 默认入池(与 scope-guard 同口径)。
- **severity 分级处置**: blocker(真缺陷/违反黄金法则/碰红线风险)**必修完才可收尾**(硬门槛); major/minor 裁量当场修或入池; nit 通常忽略但留痕。
- **收口接缝终审 ≤200 行**: 见 ②, 发现处置与批次轮拉齐。
- **修复循环**: **扳机** = 上一轮评审快照之后可评内容出现**任何新 diff** → 必走一轮(格式化也算改动, 不设"只是格式化"口子); 记账/生成物补写不触发。**载体** = 每轮 `review.pack` 照旧出**整批过滤 diff**, 评审指令限定「**只报新增改动的问题 + 校验上一轮发现未被回退**」, 上一轮发现清单随包附带 —— 已干净的代码不重新开庭。**出口** = 裁决后**零 actionable**: refute 弃、计划外入池算闭合、blocker/major/minor 当场修完。**轮次不限**, 直到某轮零 actionable。

## ⑥ checklist(通用 10 条 + 本项目面 4 条)

**通用面 6 条**(源自 Google Engineering Practices / Mozilla goal review / OWASP 子集):

1. **Goal**: 改动对准任务目标, 修根因而非症状。
2. **Design**: 与周边架构一致, 未引入平行机制。
3. **正确性**: 边界条件、错误路径、对用户与调用方都正确。
4. **Tests**: 新行为有测试、测试有意义且会真失败。
5. **可读性**: 有无更简单的等价实现; 命名传达意图; 注释解释 why 而非 what。
6. **安全面**: 硬编码凭据、日志泄敏、输入未校验。

**文档面 4 条**(文档也要评, 这几条机器判不了):

7. **事实**: 文档里的命令、路径、行号、计数在快照里真实存在且对得上。
8. **口径**: 与单点定义一致, 没有造出第二份口径; 指针指向的文件真实存在。
9. **可执行**: 照文档步骤能走通 —— 参数必填、前置条件、停手点是否写清。
10. **反面证据**: 结论是否只挑了支持自己的证据; 有没有该写而未写的反例。

**本项目面 4 条**(补充, 不占上面 10 条编号; 挂本项目约定/红线):

- **`@version` / `@grant` 一致性**: `src/*.user.js` 脚本头的 `@version` 与 `@grant` 声明与实际能力对得上, 增删权限同步改头。
- **零依赖 Node**: `tests/run-all.js` 与脚本保持零第三方依赖(Node 原生可跑), 不引入 npm 包或外部运行时依赖。
- **单文件 `.user.js`**: 交付形态是单文件 `.user.js`; 改动不把逻辑拆成需另装的伴生文件, 不引外部 CDN 运行时依赖。
- **`resources-do-not-track/` 红线**: diff 未触碰 `resources-do-not-track/`(私有整页与凭据), 也未把该目录内容复制进任何入池件。

## ⑦ 留痕

**留痕走档案/文档, 不进提交信息**。本仓库提交规范是「纯中文首行 + 空行后详述」, 不写任何评审 trailer, 也不设免评通道 —— 评审留痕只进任务档案进度日志的 `review:` 行与计划文档。

- 每批 `review:` 行记: 批次范围与规模行数、发现与处置(blocker/major/minor/nit 各几条、修/入池几条)、是否经过 `review.check`、修复轮数、接缝终审结论。
- 日期与取时一律 `commands run kb.time`, 禁用模型上下文里的日期与手工推算。
- 提交闸门不认任何评审 trailer 键; 人工抽查看档案与计划文档。`.commands/review/` 的 `review.pack` / `review.check` 只产出与校验, 不写提交信息。

## ⑧ 降级自查

无子代理能力的工具环境: 主 agent 按 ⑥ checklist **逐条**自查, 产出同 schema 的发现列表, `review.check` 照跑; 自我裁决时**从严**(相关性与严重度都取保守侧)。其余流程(评审包/校验/裁决/留痕)不变。

## 反模式

- ❌ 把评审留到收口一次做 —— 1300 行的单块评审对已知缺陷召回差, 400 行分批显著更好。
- ❌ 拿"这次改动小"当免评理由 —— 判据是可评内容 >0 行与面, 不是感觉; 1 行也要评。
- ❌ 评审快照后又改了可评内容不带新基直接提交 —— 补一轮复评而不是硬凑。
- ❌ 只写 `review:` 行不真评 —— 发现要过 `review.check` 才算数, 走过场的批次会被下一批连坐。
- ❌ reviewer 顺手修 —— 它只读; 修复一律主 agent 执行, 否则评审与实现混在同一双眼睛里。
- ❌ 引文没过 `review.check` 就采信 —— 对不上即弃, 不复核。
- ❌ 把评审结论写成 trailer 塞进提交信息 —— 留痕只进档案/文档(与本仓库提交规范冲突)。
- ❌ 超 400 行不拆批也不多派 —— 分面只是换问法, 每个子代理仍要读整块, 容量没降。
