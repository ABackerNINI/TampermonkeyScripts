# 规则写了却没生效 —— 先分清「**没匹配上**」还是「**被压住**」
> 摘要: 规则写了却没生效 —— 先分清「没匹配上」还是「被压住」：`getComputedStyle` 取到 transparent/站点默认值 ⇒ 没匹配上（补选择器），取到某个具体颜色（既非默认也非主题色）⇒ 被压住（只能 `!important`），两种故障修法完全不同。
> 触发: 没匹配上, 被压住, !important, inline style, 按属性存在兜底

- **触发**: 用户手动装了最新版（日志 `THEME_ON ... [OK]; 列映射完整`）后白底仍在；控制台探针实测：104 个 `tr.sticky_top` 全部在 `#torrenttable` 内、`R=52 / TN=52 / neither=0` —— 结构匹配完全没问题，但有 16 个（外 8 + 内 8）是 `rgb(250,238,244)`（lum 241 粉白）。
- **判别**: 两种故障修法完全不同，混在一起就会反复改错地方：`transparent` / 站点默认值 ⇒ 没匹配上（选择器够不到，补/改选择器，P65 那种直接子代够不到嵌套层）；某个具体颜色（既不是默认值也不是主题色）⇒ 被压住（选择器没错，只能 `!important`）；本例锁定为 inline `style='background:#FAEEF4'` 的三条佐证：① inline 特异性 `(1,0,0,0)` 压得过作者样式表所有选择器；② 既有 `tr[bgcolor]` 那条本来就带 `!important` —— 若是 bgcolor 属性早被压成深色了；③ inline 白底兜底只枚举 `rgb(255,255,255)/white/#fff/#ffffff`，粉白一条都不命中。
- **处置**: 四条纪律：① `!important` 不是「兜底手段」而是 inline 声明的唯一对手 —— 作者样式表的 `!important` 压得住 inline 的非 `!important` 声明（反过来不行）；② 按颜色值枚举的兜底迟早漏（P67 漏 `#ffffff` 六位写法、P76 漏粉白 `#FAEEF4`），凡是「站点可能在 inline 里写任意底色」的场景，兜底要按属性存在（如 `[style*='background']`）而非按值，实在要按值就明确写下「已知漏网值」清单别假装覆盖全了；③ 加 `!important` 必须同步检查有没有吃掉 `:hover` / `:focus`（本例底色那条会把 `R + ':hover'` 的悬停反馈一起吃掉，补了 `R + '.sticky_top:hover{...!important}'`，(1,3,2) 才压得住 (1,2,2)）；④ 跨行拼接的 CSS 字面量，静态断言的正则要容忍跨行拼接的加号空白（本例 `'...accent);'` 换行 + `'background:...'`，写成单行正则会误报，刚踩了一次害我多查一轮）；反向验证的最强形态：去掉 `!important` ⇒ 仿真里背景回落成 `rgb(250, 238, 244)`，与用户真站探针报的值一模一样 —— 这同时证明了诊断与修复，比任何推理都硬。

## P76. 规则写了却没生效 —— 先分清「**没匹配上**」还是「**被压住**」

**怎么发现的**: 用户手动装了最新版(日志 `THEME_ON ... [OK]; 列映射完整`)后白底**仍在**。
控制台探针实测: 104 个 `tr.sticky_top` **全部**在 `#torrenttable` 内、`R=52 / TN=52 / neither=0`
—— 结构匹配**完全没问题**; 但有 **16 个(外 8 + 内 8)是 `rgb(250,238,244)`**(lum 241 粉白)。

**两种故障, 修法完全不同** —— 混在一起就会反复改错地方:

| 症状(`getComputedStyle` 取到的值) | 病因 | 修法 |
|---|---|---|
| `transparent` / 站点默认值 | **没匹配上**(选择器够不到) | 补 / 改选择器(P65 那种: 直接子代够不到嵌套层) |
| **某个具体颜色**(既不是默认值也不是主题色) | **被压住** | 选择器没错, 只能 `!important` |

本例锁定为 **inline `style="background:#FAEEF4"`** 的三条佐证:
① inline 特异性 `(1,0,0,0)` 压得过作者样式表所有选择器;
② 既有 `tr[bgcolor]` 那条**本来就带 `!important`** —— 若是 bgcolor 属性, 早被压成深色了;
③ inline **白**底兜底只枚举 `rgb(255,255,255)/white/#fff/#ffffff`, **粉白一条都不命中**。

**四条纪律**:
1. **`!important` 不是"兜底手段", 是 inline 声明的唯一对手** ——
   作者样式表的 `!important` **压得住** inline 的非 `!important` 声明(反过来不行)。
2. **按颜色值枚举的兜底迟早漏**: P67 漏 `#ffffff` 六位写法、P76 漏粉白 `#FAEEF4`。
   凡是"站点可能在 inline 里写任意底色"的场景, 兜底要按**属性存在**(如 `[style*="background"]`)
   而非按值 —— 实在要按值, 就明确写下"已知漏网值"清单, 别假装覆盖全了。
3. **加 `!important` 必须同步检查有没有吃掉 `:hover` / `:focus`** ——
   本例底色那条会把 `R + ':hover'` 的悬停反馈一起吃掉, 补了
   `R + '.sticky_top:hover{...!important}'`((1,3,2) 才压得住 (1,2,2))。
4. **跨行拼接的 CSS 字面量, 静态断言的正则要容忍 `'\s*\+\s*'`** ——
   本例 `'...accent);' \n + 'background:...'`, 写成单行正则会**误报**(刚踩了一次, 害我多查一轮)。

**反向验证的最强形态**: 去掉 `!important` ⇒ 仿真里背景回落成 **`rgb(250, 238, 244)`**,
与用户真站探针报的值**一模一样** —— 这同时证明了诊断与修复, 比任何推理都硬。
