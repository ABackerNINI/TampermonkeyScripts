# 版本管理
> 摘要: 改码必同步递增 @version 的规则 / 自查清单 / 提交信息规范
> 触发: 递增版本号, 写提交信息, 提交前

## 1. 版本管理

### 铁律：修改代码 ⇒ 同步递增版本号

- **任何代码/元数据的改动，都必须递增脚本头 `@version`**，与代码修改放在**同一次提交**中（不允许「改了代码但忘了版本号」的提交）。
- 原因：Tampermonkey 依据 `@version` 判断脚本是否有新版本（结合 `@downloadURL` / `@updateURL` 自动更新）；版本号不变则用户端**永远不会收到你的修复**。
- 版本号递增规则：`YYYY.MM.DD.N`
  - 跨天修改：`YYYY.MM.DD.1`（如 `2026.08.30.1` → `2026.09.07.1`）；
  - 同一天多次修改：`N` 递增（`2026.09.07.1` → `2026.09.07.2`）。
- ⚠️ **日期后的小版本号 `N` 跟随日期重置**：一旦日期段（`YYYY.MM.DD`）变化，`N` 必须从 `.1` 重新计，**绝不沿用前一天的计数继续递增**（如 09-07 最后一次是 `2026.09.07.11`，09-08 的首次修改应为 `2026.09.08.1`，而不是 `2026.09.08.12`）。否则同一天序号会跨天虚高，失去「当日第几次修改」的语义。
  - 违例实例（2026-09-08 已发生，勿再犯）：09-07 末次 `2026.09.07.11`，09-08 两次提交却写成 `2026.09.08.12/.13`，本应为 `2026.09.08.1/.2`。

### 何时必须递增版本号

| 改动类型 | 是否递增 | 说明 |
|----------|:--------:|------|
| 修复 Bug / 新增功能 / 调整逻辑 | ✅ 必须 | 任何行为变化 |
| 修改 `@match` / `@description` / `@grant` 等元数据 | ✅ 必须 | 影响匹配范围/权限/说明 |
| 纯注释 / 代码格式化 | ⬜ 不必（建议不递增） | 不产生行为差异 |
| 只改 `memory-bank/` 知识库文档 | ⬜ 不必 | 不涉及脚本本体 |

### 提交前自查

1. 本次改动的脚本头 `@version` 是否已递增？
2. 版本号是否符合 `YYYY.MM.DD.N`（跨天重置 N、同日递增 N）？
3. 是否与代码改动在**同一次提交**中？
4. 改动行为时，`@description` 是否需要同步更新？
5. **是否夹带了私有资源 / 凭据？** `git status --porcelain -uall` 与 `git diff --name-only` 中不得出现
   `resources-do-not-track/` 下的路径；待提交内容中不得含真实 passkey / token / cookie（见第 0.5 节）。

### 提交信息规范（规范且详细）

- 提交信息用中文；**首行概括 + 正文详述**，禁止只写一句含糊的话。
- 格式建议：
  ```
  <类型><对象>: <一句话概括>

  - <背景/原因>
  - <改动要点，分条列出>
  - <影响/注意事项，如涉及站点、行为变化、版本号>
  ```
- 类型前缀：`添加` / `修复` / `调整` / `重构` / `文档` / `测试`（如「修复BTSchoolHelper时魔解析」）。
- 示例：
  ```
  修复BTSchoolHelper时魔值恒为0

  - 原因: calcA/calcAve 用 parseCommaIntSafe 解析浮点属性导致 NaN
  - 修复: 改用 parseCommaNumberSafe; 版本号 2026.09.07.1 -> 2026.09.07.2
  - 影响: 依赖时魔数值的排序/筛选恢复正常
  ```
- 一次提交只做一件事：一个 Bug / 一个功能，连同其**版本号递增与知识库同步**放入同一次提交（见第 0.4 节）。
