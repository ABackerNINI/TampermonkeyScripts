§01目标与设计原则

目标 — 把 auto-qb 已落地的轨道改造能力(配置/数据外置、宽容回落 + 必打提示、fail-closed 守卫显式挂载、PORTING 轨道 runbook、glob 化闸门匹配、环境中立模板)移植到本项目的同名轨道, 使本项目自身也满足「拷轨道 + 填少量配置 + 零代码 diff 可移植」; 同时把 auto-qb AGENTS.md 中真正通用的口径增量补齐。成态判据: 本项目的既有行为、项目铁律与用户可见默认值零漂移。

不变量(硬约束):

  1. 本轮零实施 — 本篇是计划; 不改代码、不改配置、不入池 issue、不 commit/push; 实施须用户逐项授权(新建文件 / 入池 / 认领 / commit 四类动作分别确认)。
  2. 项目身份不动摇 — 本项目是「长期装机使用的个人生产脚本 + 纯 Node 零依赖测试栈 + 无 package.json」; auto-qb 的 uv / Docker testbed / qB 真机 / pytest TMPDIR 自举一律不进本项目。
  3. 行为零漂移 — 现有 `commands run` 入口、`test.full`、闸门触发面、`AGENTS.md` 项目铁律 1–5、红线清单在移植后保持原语义; 任何变更须有迁移对照表证明意图未丢。
  4. 跨仓红线零消耗 — 只读 auto-qb 的文档/配置/清单; 不复写、不在其目录跑 git; 移植产物只落本 clone。
  5. 版本与知识库同步 — 实施轮每批改任何脚本/元数据必须同批递增脚本头 @version 并回写 memory-bank/ 受影响条目(项目铁律 3/4); 本批只写方案文档, 无脚本改动故不触发。

取舍口径(源自 grilling, 详见 §06): 移植单位是改造涉及、两仓共有的轨道件, 不是整套 auto-qb 目录; 配置值从本项目现状推导、不为移植而改行为; 缓行项只登记不实施; 验收绑定本项目五道闸 + 沙箱重放。
