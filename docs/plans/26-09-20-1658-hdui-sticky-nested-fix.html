第二段置顶种子白底·诊断与修复计划

用户实拍（屏幕截图 2026-09-20 165720.png）发现种子列表中带「热门」标签的置顶行第二段背景为白色。 本计划定位根因、给出最小修复、并列出可机械验收的检查项。

01症状与定位

用户描述

「第二段置顶种子仍是白色背景」—— 即种子列表中带「热门」置顶标识的行， 其中部分行的背景仍为站点默认白底，未跟随主题上色。

观察事实（真站探测，2026-09-19 .25 实施时已做）

  • 真站 #torrenttable 内 tr.sticky_top 共 86 个。
  • 其中 43 个位于 #torrenttable > tbody > tr（外层种子行）。
  • 另 43 个位于 #torrenttable table.torrentname > tbody > tr（标题格内嵌表里的行）。
  • 上妆后背景探测：43 themed（rgb(32,28,24)）+ 43 透明（露出站点默认白底）。
  • 行 class 完全相同（都是 sticky_top），但选择器只命中其中一半 —— 这正是症状的成因。

对照截图

用户截图中的「第二段置顶种子」白底 —— 即站点种子列表中某一条标题格内嵌的置顶行 （典型形态：外层行已上色、内嵌标题格那条仍白），与 .25 实施时复现的 bug 同源。

02根因分析

选择器特异性盲区

胶片墙主题 CSS 里的置顶规则写法：

// src/HDHomeUI.user.js:644
const R  = '#torrenttable > tbody > tr:not(.colhead)';
const TN = '#torrenttable table.torrentname > tbody > tr';

// src/HDHomeUI.user.js:762
R + '.sticky_top{box-shadow:inset 3px 0 0 var(--hdui-accent);}';

R 是直接子代选择器（>），只能命中 #torrenttable > tbody > tr 这一层。 标题格里嵌套的 <table class="torrentname"> 同样有 tbody > tr.sticky_top，但属于 间接后代（隔了一层 <td> → <table> → <tbody>），选择器够不到。

为什么之前没暴露

  • 仿真页从原型派生（film.html 与 torrentname 内嵌表的「置顶嵌套行」结构是 .11/.12 才被加回仿真）。
  • 原站 DOM 嵌套表非常常见，同 class 出现在两层是种子列表的常态 —— 不是边缘 case。
  • 漏白扫描只跑「可见 + 大面积 + 亮度 > 200」：标题格里的内层行面积小，且被外层深色块「遮一半」视觉上能蒙混过关。

判据复盘（P49 / P65 一脉相承）

凡是「DOM 选择器匹配数 ≠ 应有元素数」的规则，都有理由怀疑漏了某种结构。 这条 86 个 tr.sticky_top，但只有 43 个 themed —— 一眼看出漏了一半。

03修复方案

最小修复（一行 CSS）

// src/HDHomeUI.user.js:770（已写入 .25）
TN + '.sticky_top{background:var(--hdui-card);}';
选择器命中数（修前）命中数（修后预期）
R + '.sticky_top'43 / 8643 / 86
TN + '.sticky_top'（新增）0 / 8643 / 86
合计 themed43 / 8686 / 86

为什么「只加背景不加金边」

  • 外层那条 R + '.sticky_top' 的 box-shadow:inset 3px 0 0 var(--hdui-accent) 金条只在种子行左缘生效 —— 它作用在外层 <tr> 的盒子上，视觉位置是行首。
  • 嵌套内层 <tr> 是标题格里的小行，再加一条金边会出现内外双金条（用户视觉负担 + 与「行首置顶」的语义重复）。
  • 置顶的视觉语义已经由外层金边承担；内层只需要「底色跟上主题」即可。

不动的部分

  • 不引入通用后代选择器（#torrenttable .sticky_top 一把梭）—— 会意外命中 meta 格里的嵌套表（豆瓣 IMDb + 下载收藏），而那些 <tr> 没有 sticky_top class，命中为 0；将来站点若加 class，泛化规则反而扩大打击面。
  • 不动 R 的定义 —— 直接子代选择器对其它规则（行高、padding、frame counter）仍是正确的最小作用域。
  • 不动外层 R + '.sticky_top' 的金边 —— 视觉锚点保留。

04回归与验收

静态防线（tests/hdhomeui/check-hdui-static.js）

  • 规则存在性 — 在产物 CSS 中能找到 TN + '.sticky_top{background:var(--hdui-card)}'（防规则被误删）。
  • 无金边覆盖 — 嵌套选择器不能包含 box-shadow:inset 3px 0 0 var(--hdui-accent)，避免内外双金条。
  • 作用域最小 — 该规则不与 R + '.sticky_top' 合并到通用后代选择器（保留直接子代的精确性）。

仿真用例（tests/hdhomeui/sim-hdui-meta-actions.js 或新文件）

  • 仿真页构造 — 在 torrentname 内嵌表里加一行 tr.sticky_top（含「热门」标识），模拟真站嵌套结构。
  • 底色断言 — 该行的 getComputedStyle().backgroundColor 应解析为 rgb(32,28,24)（即 --hdui-card），非 transparent。
  • 无金边断言 — 该行 box-shadow 应为空（无 inset 3px 0 0），保证不会内外双金条。
  • 外层金边保留 — 同行的外层 tr.sticky_top 仍应有 inset 3px 0 0 rgb(245,179,66) 金边。

真站验收（.workbuddy-ai/_verify-hdui-real-render.js）

  • 86/86 themed — 真站所有 tr.sticky_top 的 background-color 不为 transparent 且不等于 #ffffff。
  • 漏白扫描 — scanWhite 在标题格嵌套表区域返回 0 条告警。
  • 小件近白扫描 — scanNearWhite 在同区域返回 0 条告警。
  • 几何对齐 — 嵌套行不撑高外层（行高 / padding / frame counter 保持不变）。

反向验证（必做）

删掉 TN + '.sticky_top{...}' 这一行 → 重跑仿真 + 真站 → 必须恢复为「43 themed + 43 transparent」才视为修复有效。

05影响面与风险

维度评估
影响范围仅嵌套 tr.sticky_top 的底色（≈43 个元素），其余 0 改动。
性能新增一条 CSS 规则、零 JS 改动，可忽略。
回归风险低 —— 只动 background，不碰 box-shadow / display / 盒模型。
未知站结构若站点将来在 torrentname 之外的其它嵌套表里给 tr 加 sticky_top，本规则不命中 —— 需再次复盘。
跨主题本规则写在 filmCss()（胶片墙专属）。其它主题各自实现置顶样式，但目前已无其它主题（.7 移除）—— 风险为 0。

06实测结论与当前状态

⚠️ 修正：本表初版写「静态 / 仿真 / 真站验收全缺」是基于不完整阅读，实测后推翻。 三项其实都已存在（check-hdui-static.js:446、verify-hdui-real-page.js:247、 sim-hdui-theme-switch.js:46）。真正的问题是**断言强度不足**，不是缺失。

核心结论：代码侧修复早已生效，本轮不需要改行为。 真站样本上 86 个 tr.sticky_top（外 43 + 内 43）全部 self=29 深色； 置顶验收 86/86、漏白 / 小件近白双双干净；全页 lum>120 的只剩 span.tags 的 23 种分类色（TASK019 用户拍板刻意保留）与一个金色 a。 ⇒ 用户所见高度疑似跑在 .25 之前的旧版本。

三类切分：先证伪自己的结论，再下判断

初版探针只按「在不在 table.torrentname 里」二分 —— 若存在既不匹配 R 也不匹配 TN 的第三层置顶行，会被误分类成「外层」， 那么「修复已生效」的结论就不成立。补做三类切分实测： all=86, byR=43, byTN=43, both=0, neither=0 —— 43 + 43 正好等于 86， 不存在第三层，结论站得住。

已固化为 verify-hdui-real-page.js 的新断言 all === byR + byTN 且 neither === 0。 ⚠️ 它验的是 DOM 结构不是 CSS 覆盖 —— 删 CSS 不会让它变红， 反向验证必须注入一个合成的同 class 嵌套行（实测注入后 neither 0 → 1，确认可证伪）。 教训：只断言「这几个都盖住了」，证明不了「没有下一层」—— 覆盖类断言要配一条结构类断言兜底。

「透明 ≠ 白」—— 为什么扫描抓不到这个 bug

把修复删掉后重跑真站验收，报「共 86 个，透明 43 个」—— 但漏白与小件近白两条扫描依然报干净。原因：内层 tr 是 transparent，透出的是外层那条已经上妆的深色 card，视觉上根本不是一块白。 两档扫描看的都是「元素自身声明了亮色」，抓不到「本来该有底色、结果没有」这种声明缺失。

08备选方案与拒绝理由

方案做法拒绝理由
通用后代选择器 #torrenttable .sticky_top{...} 一次性命中两层 扩大打击面 —— meta 格嵌套表若将来出现同名 class 会被误命中；且与「最小作用域」的工程纪律不符。
JS 遍历修补 applyStored 里给嵌套 tr.sticky_top 加 style.background 违反铁律（不重建 DOM、不改 inline style）；CSS 可解的问题不要用 JS。
不修内层 接受视觉白底，靠外层金边承担「置顶」语义 用户已实拍报为 bug，置顶行的视觉一致性是基础体验。
整条规则下沉到 #torrenttable 下 把置顶样式从行级下沉到列级（按列选） 与现行「每列一个 nth-child 槽位」的排版约定冲突；改动面过大。
